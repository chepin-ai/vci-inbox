## WQ-1 「可恢复」叙事缺少跳闸线——治理缺口本身即缺陷

**质疑**：蒸发频率批十二 1 次 → 批十三 2 次+在途（v56 自记「蒸发频率显著上升，与 merge/写活动窗相关」），六起计数 223→253→257→1→278→270 项。联邦叙事停留在「对象库完好、checkout 全恢复、零损失」，但**全档检索不到任何一条事先量化的升级阈值**：几次/批、连续几批、单日累计多少 D 项，触发「修复仪式→架构迁移」？没有跳闸线，「可恢复」就成为可无限事后合理化的叙事——每一次事件都能被逐次吸收为「又一次成功修复」，而趋势恶化永不在任何单一事件中被承认。

**后果推演（最坏情形）**：若频率按当前趋势翻倍至每批 4+ 次且外溢至 board/library（B1 已警 R2），无人值守窗口内一次蒸发 + 修复仪式未及执行即收批提交，path-limited add 纪律虽防裹入，但批末扫描若超时（见 WQ-2）将同时失去探测。量化：board/library 合计为联邦全部不可再生交付物（~150+ 在案文件），一次未检出蒸发 = 自上次 push 以来全部批次工作暴露于真损。

**检验方法**：① 本批即提案并表决书面跳闸线（建议候选：任一路径越出 weave/ 一次即架构评审；fsck 失败一次即迁移；修复频率 >1/批 连续 3 批强制评审；批末 D 扫描 rc=124 一次即探测失效警报）。② 回测：将候选阈值套用于批十→十三已发数据，回答「若有此线，我们此刻是否已越线」——按「>1/批」口径，批十三已越线。**不确定处**：蒸发真因未定位（见 WQ-7），频率趋势是环境恶化还是写负载增长的伴生现象，无数据可区分。

## WQ-2 心跳道正在杀死自己的探测器——4277 件已致 status >90s 超时

**质疑**：weave/pulse 每 ~10 分钟一拍，tracked 已达 4277 件且以 ~100–150 件/日单调增长；B1 实测全树 `git status` **>90s rc=124 超时**。而批末修复仪式恰恰依赖 `git status --porcelain` D 项扫描。这意味着：金丝雀（心跳道）的体量增长正在逼近探测仪式自身的失效点。**现行协议内含一个自毁结构**：探测器的失效不是是否问题，而是时间问题，且失效方式是静默的（rc=124 若被当「干净」处理即探测全盲）。

**后果推演（最坏情形）**：扫描超时之日 = 蒸发探测归零之日。此后蒸发频率不可见，WQ-1 的跳闸线即使有也无量可测。量化：以 +150 件/日、超时阈值 ~4300–5000 件粗估（单点实测外推，不确定），窗口已在**天级**而非月级。另：心跳 ~51min 空拍（B1 §四异常2）若系心跳停摆而非批节奏间歇，则「心跳还活着」这一前提本身未证实——心跳道可能已死，我们仍在为它的攻击面付成本。

**检验方法**：① 实测超时临界点：`git status --porcelain -- weave/pulse`（path-limited）在不同件数下的耗时曲线，一批内可得。② 核查批末扫描脚本对 rc=124 的处理分支——若超时与零 D 项不可区分，**即日修补**，此为现行协议可验证的具体漏洞。③ 核对 pulse.log 空拍原因（workflow run 记录），区分停摆/间歇。

## WQ-3 心跳的信息价值 vs 攻击面成本——账从未算过

**质疑**：shadow-pulse.yml 每拍 `os.makedirs + 写 json + git add || true`。价值侧：B1 自证 classify-sweep/pub-guard 已把 weave/pulse 列为 EXEMPT **跳过不读**——联邦内部消费为零；残余价值 = 公域影子引擎展示 + 蒸发金丝雀。成本侧：4277 件小文件高频写，作用于一个「100MB 上限/慢写/stale-index/partial-write」前科俱全的 FS，且 v56 已记蒸发「与 merge/写活动窗相关」。**若相关成立为因果，心跳就是蒸发的放大器**：我们用制造攻击面的方式来监视攻击面。

**后果推演（最坏情形）**：若心跳是蒸发诱因，则全部六起 weave/pulse 蒸发系自伤；降拍或停拍后蒸发率应显著下降——若不降，反而排除该假说（此为本条的可证伪性）。量化成本：即使无关因果，心跳每年贡献 ~5 万 tracked 小文件，线性推高 status/checkout/修复仪式成本与超时风险（WQ-2）。

**检验方法**：受控实验——① 降拍 10min→60min 观察 2 批，对比 D 项/批发生率（基线：批十三 ~2 起/批）；或 ② 改写到 scratch 目录（untracked）一周， weave/pulse 只读。信息价值替代：金丝雀职能可由 board/ 下 1 个 sentinel 小文件 + 每批 hash 校验承担，成本为 1 件而非 4277 件。**不确定处**：公域影子引擎的外部消费方是否存在、其依赖程度，本席无数据；停拍的外部影响须由枢评估。

## WQ-4 二元信任模型已被自家 FINDING 推翻，叙事未更新

**质疑**：联邦心智模型为「持久层（portal）可信、临时层（/tmp）不可信」，九起命名空间擦除全部位于 /tmp 似在强化此模型。但 **weave/pulse 六次蒸发全部发生在 portal 层工作树**（vci-inbox 工作树即 portal FS），外加 FINDING-20261024-02（portal git 半落盘：树落盘、HEAD ref 丢失、stale HEAD.lock）。门户层证据已有：工作树蒸发 ×6 + 引用写半持久 ×1 + stale-index/partial-write 前科。**二元模型不是「过度自信」，是已被在案证据证伪**——portal 只是敌意更低、失效模式不同的另一个不可信层，而现行协议的备份拓扑假设（WQ-5）仍按二元模型设计。

**后果推演（最坏情形）**：按「portal 可信」假设配置的防护（如把 /tmp 构建证据快照回 /mnt/agents/output/——同一 portal FS）实为同域备份，见 WQ-5。若 portal 失效模式从「工作树蒸发」演进到「对象库损坏」（partial-write 写 pack 时中断即可能），现行「对象库完好」的恢复前提整体垮塌。

**检验方法**：① 行文层面：对抗环境协议文档的模型陈述与 FINDING-20261024-02/-03 逐条对读，列出所有以「portal 持久可信」为前提的条款（推送验证、快照位置、修复仪式）——一批内可完成的纯文本审计。② 实证层面：对 .git/objects 跑一次 `git fsck --full --strict`，给出对象库健康基线（截至本件在案，无人做过，见 WQ-6）。

## WQ-5 无人值守窗口 + 对象库同损：备份拓扑存在同域单点

**质疑**：修复仪式靠人工/半人工 checkout，前提是「对象库完好」+「有人巡批」。两个前提均无保障条款：批间存在无人窗口（pulse 空拍 51min 才被发现即为例证——连 10 分钟心跳停了都近一小时无人察觉）；而所谓备份，B1 §三建议的 .ltar portal 外归档尚未执行，J5 构建证据快照在 /mnt/agents/output/fgl-build-log/——**与 vci-inbox 同一 /mnt/agents/output 文件系统，同一失效域**。远端 GitHub（经 ghfast.top）是唯一异域副本，但只覆盖已 push 链；staging 区（git add 未 commit 的 dangling blob）与未推送提交均为本地孤本。

**后果推演（最坏情形）**：无人窗口内 portal FS 级事件（蒸发升级为目录级或 .git 级）：(a) 未推送提交真损——按批十三节奏每批 ~4 提交，单批工作全损；(b) 若恰逢 merge 后 push 前窗口（FINDING-20261024-02 证明此窗口的半落盘风险为实），merge 树在、ref 丢、无人知，下批开工即在残缺状态上叠加；(c) J5 级 4.5h 构建证据与源命名空间同域同殉，重跑成本 4.5h×N + toolchain 重取（FINDING-20261023-04 已证 toolchain 同殉先例）。量化：单批真损上限 = 一批全部交付物（历史峰值 8 文件/5 提交量级）；J5 级重跑 = ≥4.5h 算力窗 + 重取证。

**检验方法**：① 拓扑盘点：列出全部关键资产 × 副本位置 × 失效域，标注同域对——半批可完成。② 实测隔离副本可读性：从远端 clone 一次验证批十三 HEAD（f05e35274）全链可达（此亦同时检验 WQ-8 代理锚）。③ 检查 staging 暴露面：`git fsck --lost-found` 统计 dangling blob 数，量化未提交保护窗。

## WQ-6 「对象库完好、修复 D=0」从未被证明——零损失声明悬置

**质疑**（本席自评最尖锐一条）：六起蒸发的修复闭环证据均为「checkout 恢复 D=0」+「抽样 blob 可达（cat-file -e）」。但 **D=0 只证明工作树与 index/HEAD 一致，不证明内容正确**：在 partial-write 前科的 FS 上，blob/pack 可被静默损坏而仍存在；cat-file -e 只验证单对象可解析，且均为**抽样**——六起修复后无任何一次 `git fsck --full` 或全量 hash 比对在案。更深处：若 index 本身曾与工作树同殉（stale-index 前科），checkout 恢复的「一致」可能是「一致地错」。**「零损失」是现行修复叙事的承重墙，而这面墙从未被全量验证过。**

**后果推演（最坏情形）**：静默损坏的 pulse blob 已进入已 push 链（公域 pulse 链 359+ 提交在远端），则公域影子引擎一直在服务损坏快照而无人可知；若损坏落在 board/library/specs 的 blob 上且已推远端，联邦证据链完整性溯及既往地存疑。量化：weave/pulse 4277 件 + 全仓其余路径，一次全量 fsck 在 2 核机上预计分钟级——验证成本与风险敞口严重不对称，不做无理由。

**检验方法**：① 立即一次性 `git fsck --full --strict` + `git rev-list --objects --all | git cat-file --batch-check` 全量对象可解析性核验；② 与远端异源比对：fresh clone 后 `git log --format=%H` 全链 + 关键交付文件 hash 对拍；③ 此后每次修复仪式追加 fsck 快检入规程。**不确定处**：portal partial-write 是否会影响已 fsync 过的 pack 读侧，取决于 FS 实现，本席无 portal 内部规格——但正因如此才须以全量校验代替假设。

## WQ-7 六次复发零归因——修复仪式在治疗一个未诊断的病

**质疑**：六起蒸发 + 一起半落盘，全部处置止于「修复 + 闭环」，**无一例根因分析在案**：是 unlink 风暴（cleanup 进程）？git 操作触发（v56 记「与 merge/写活动窗相关」）？portal FS 配额/回收策略？FINDING-20261024-03 记「演进登记：unlink 噪音无害」——「无害」结论的依据未见。「与写活动窗相关」是唯一的因果线索，却未转化为任何受控实验（WQ-3 的降拍实验即可兼测此条）。六起同源事件零归因，在对家模型下等同于：对手（或环境失效进程）的能力边界、触发条件、演进方向全部未知，而我方防御全部建立在「它只会碰 weave/pulse 的工作树、永不碰对象库」这一**无证据的行为假设**上。

**后果推演（最坏情形）**：失效进程行为漂移（路径外溢或深入 .git），首次越界事件即击穿全部既有假设；因无基线行为模型，漂移本身可能晚一批才被察觉。量化：WQ-4/WQ-5/WQ-6 的最坏情形在本条下叠加放大。

**检验方法**：① 低成本取证： weave/pulse 目录 mtime/ctime 快照每批留存 + 蒸发事件前后窗口比对，推断蒸发时间粒度（批量瞬时 vs 渐进）；② 受控写实验（WQ-3 同款）；③ 若 portal 提供任何审计/日志接口，调取 10-23→10-25 窗口——此点依赖平台能力，**不确定**，须向枢确认可及性。

## WQ-8 双验证规程的真值锚单一：ls-remote 全走 ghfast.top 代理

**质疑**：FINDING-20261024-02 后入册新规程「push 后必 ls-remote 验证真值，禁信管道 RC」——方向正确，但 ls-remote 的网络路径是 ghfast.top 镜像代理（B2′ RERUN-02 记 ghfast 降速改 gh-proxy 竞速，代理链本身不稳定在案）。**「不信管道 RC、信 ls-remote」只是把信任从本地管道转移到单一第三方代理**：代理被污染/劫持/中间人时，可返回伪造的远端 ref——push 实际失败而验证「通过」；或反之谎报失败诱发重复推送。现行规程对代理无任何交叉锚。

**后果推演（最坏情形）**：假阳性验证 + 随后本地 .git 受损（WQ-5 情景）→ 一批工作在「已验证上链」的确信中真损。量化：单批 ~4–5 提交量级全损；若污染持续多批且本地逐批滚动，敞口线性累计。另注意 B1 §三 cache 去 Azure 化：联邦对代理/镜像的依赖面在扩大而非收缩。

**检验方法**：① 交叉锚立即可行：ls-remote（代理）与 api.github.com 直连 `GET /repos/.../commits/{sha}`（B1 §三已实证 api.github.com 直连可用）双通道比对，sha 一致才记账——增量成本每批一次 API 调用；② 抽样 fresh clone 全链核验（WQ-5②/WQ-6② 同一次操作三用）；③ 长期：commit/tag 签名。**不确定处**：ghfast.top 的信任属性、运营方、是否存在端到端完整性校验（如 TLS 证书钉），本席无资料，须平台侧确认。

## 附：对 B1 NO-GO 论证的重估（WQ 方向 6）

B1 的 NO-GO 以 R1（写入流静默降级）为单独否决项，论证成立——但**否决的对象是「现状形方案」，而 R1 恰是五行 workflow 修改即可消除的风险**（`git add --sparse` + 去 `|| true` + 失败告警）。真正未被充分定价的是 R4（sparse 位写在 stale-index 前科的 index 上，可能同殉）——B1 标注「未测」即止。重估后成本收益：

- **条件式 GO 的真实前置成本**：workflow 修改（小）+ 2 批观察（中）+ R4 实测（小，一批内可对 sparse 位做写后读回压测）——总成本低于 B1 行文的暗示。
- **但收益侧随 WQ-2/WQ-3 重估后方向改变**：若心跳降拍/改道实验（WQ-3）成立，4277 件心跳道本身应缩编或退役，sparse 排除的对象可能不复存在——**sparse 议题应让位于心跳道存废议题，二者不应独立裁决**。
- B1 低成本替代（修复仪式脚本化 + canary 保留）与 WQ-2 冲突：canary 体量正是探测器超时的成因，「保留 canary」须有体量上限或改为 sentinel 制，否则替代方案内含同样的自毁结构。

**本席不裁 GO/NO-GO，仅指出：三项议题（sparse 排除、心跳道存废、探测器超时）共享同一变量（weave/pulse 体量），应并案裁决。**
