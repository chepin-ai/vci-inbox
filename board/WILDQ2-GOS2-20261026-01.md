## §1 挑战：comparator 退出码全程不设闸——「打印 accepted 后崩溃」即产出 accepted 回填证据

- **挑战**：W11 草案 §一 `Comparator run` 步骤捕获 `RC` 并写 `comparator_rc` 入 `$GITHUB_OUTPUT`，但**全 workflow 无任何环节以 `comparator_rc` 为闸**；步骤末命令为 `echo`，故 comparator 以任意非零码退出（含 `lake comparator` 子命令不存在 rc=127、段错误 rc=139）该步仍绿。下游 `Verdict` 步骤的唯一事实源是日志 grep——**只要崩溃前已写出 `verdict: accepted` 行**（部分跑批、结果缓存命中早退、子进程先打印后主进程崩溃），verdict.txt 即落 `accepted`，五项验证规程（GAPCLOSE §2.3）无一检查 comparator 出口码。
- **依据钉**：W11 草案 §一 yaml L106–115（`|| RC=$?` 后无 `exit`、无 `if`）；L117–130（verdict 仅 grep）；GAPCLOSE §2.3 验证 1–5（无退出码项）；W10″ 定稿 §二 09:40–09:45 行（绿灯确认＝run conclusion，不查 comparator_rc）。
- **查验路径**：合入前以桩 comparator（`echo 'verdict: accepted'; exit 3`）dry-run 一次，观察 workflow 是否伪绿——若绿则漏洞实证。
- **建议处置**：`Comparator run` 步骤尾部加 `[ $RC -eq 0 ] || exit $RC`（rc≠0 即红、不进 verdict 步骤）；GAPCLOSE §2.3 增列「验证 0：run conclusion=success ∧ comparator 步骤 conclusion=success」。**不处置则 B-1 闭合件自带伪绿通道。**

## §2 挑战：verdict 取值语义是「最后一处匹配行」而非「日志末行」——合并流后注入行可覆盖真 verdict（透传伪造面）

- **挑战**：草案自注「verdict 逐字取自日志末行」，实现却是 `grep -E '^verdict: (accepted|rejected)$' comparator-run.log | tail -1`——语义为**全文最后一处匹配行**。stdout+stderr 合并流（`2>&1 | tee`）下，comparator 真输出 `verdict: rejected` 之后，**任何**后继写流（comparator 子进程继承 fd、收尾警告、shell 自身诊断、乃至 runner 注入的 stderr 行）只要含一行 `verdict: accepted`，tail -1 即取伪值。GAPCLOSE §2.3 验证 4「日志末段 verdict 行与字段逐字一致」为自洽性校验（同一来源对拍同一来源），不构成防伪——**verdict.txt 与回填值同源同伪，五验全过**。
- **依据钉**：W11 草案 §一 yaml L112（合并流）、L122（grep|tail -1 实现）、L121 注释自称「末行」与实现不符；GAPCLOSE §2.1 log_sha256 行（合并流为规范件）、§2.3-4（自洽性对拍）。
- **查验路径**：构造日志：`verdict: rejected`（第 N 行）＋尾部任意 `verdict: accepted` 行，跑草案取值段，观察 verdict.txt 落 accepted——伪造面实证；另查 nanoda/comparator 是否在 verdict 行后还有任何输出（决定天然暴露面大小）。
- **建议处置**：取值改为「**物理末行**匹配」（`tail -n 5` 窗口内正则匹配且要求匹配行即最后一非空行）；或 comparator 侧以 exit code 承载 verdict（0=accepted／42=rejected 之类，沿 R2B-02 退出码契约化体例，FSL v59 在案），日志行仅作展示。二者至少取一；现状形态禁入 formal 跑批。

## §3 挑战：dry-run 与 formal 产物同形同包同名，`mode` 行不在五项验证规程内——输入校验钉而不死

- **挑战**：`mode` 输入经 `type: choice` 限定（UI/API 层校验在位），但 **workflow 本体无任何步骤依 mode 分支**——mode 唯一去向是写入 verdict.txt 第三行。后果：dry-run 跑出的 artifact 与 formal 跑**文件名、artifact 名、字段形态全同**，唯一区分是 `mode: dry-run` 一行；而 GAPCLOSE §2.3 五项验证无一读取 mode。A1.1 钉要求 dry-run「四要件全实证（含 comparator 实跑）」——这意味着 dry-run artifact 的 verdict/log_sha256 同样「看着有效」。任何人（或 §4 的脚本缺陷）取到 dry-run 的 run_id，回填后五验全过，责任窗以空转证据伪闭合。
- **依据钉**：W11 草案 §一 yaml L45–54（mode 定义）、L126–130（mode 仅写入文件、无分支）；§二 A1.1（dry-run 全要素）；GAPCLOSE §2.3（五项无 mode 项）。
- **查验路径**：grep 草案全文确认无 `if: .*inputs.mode`；对照 §2.3 五项逐条确认无 mode 校验（本席已做，确认）。
- **建议处置**：三选一或叠加——① formal 模式 artifact 名加后缀（如 `m1-b1-comparator-run-formal`）；② §2.3 增列「验证：verdict.txt `mode: formal` 逐字」；③ dry-run 模式 verdict.txt 文件名改为 `verdict.dryrun.txt`。最省为②，但①根治下载侧误取。

## §4 挑战：A2.2 取值脚本结构性失灵——全局 runs 清单 `per_page=3` 在 54 件 active workflow＋10min pulse 节拍下几乎必错

- **挑战**：B-2 随件脚本查询 `GET /actions/runs?per_page=3`（**全仓所有 workflow** 的最近 3 个 run），再按 name 过滤取 `[0]`。三个独立失灵面：①**空集崩溃**：W11 草案 §〇实测 54 件 active workflow、pulse 远端心跳 10–24min/拍（庭备件 §二钉 2）——若任一 push 触发型 workflow 在册，m1-b1-baseline 的 run 大概率不在最新 3 条内，`[w for w in runs if ...][0]` 抛 IndexError（执行日 09:08–09:10 的 2 分钟窗口内当场炸）；②**错取更晚 run**：不过滤 conclusion/status——若 formal 跑后又有任何同名 dispatch（含 dry-run、含失败重触发），`[0]` 取到更晚者，与 §3 叠加即空转证据回填；③**不过滤 head_branch**（见 §9 A1.4）。
- **依据钉**：W11 草案 §二末代码块（`runs?per_page=3`、`[0]`）；§〇表（54 件 active）；庭备件 §二钉 2（pulse 9 拍/2.5h 区间实测）；W10″ 定稿 §二 09:08–09:10 行（脚本取值仅 2m 预算）。
- **查验路径**：本机以现脚本对仓实测一次（只读 GET）：打印最新 3 个 run 的 name 清单——若 m1-b1-baseline 不在其中（当前它根本不存在，100% 不在），空集面即实证；正确端点为 `GET /actions/workflows/<workflow_id>/runs?per_page=1`。
- **建议处置**：脚本改专用端点＋过滤 `status=completed, conclusion=success`＋校验 `head_branch=main`＋空集显式报错转分支甲；`gha:<id>#<attempt>` 输出与 dispatch 时刻对拍（run created_at ≥ dispatch 时刻）。

## §5 挑战：cache get「断供而 rc=0」面未封＋workflow 无 wall 硬封——410s 先例不构成时长上限，≤3h 封钉在 CI 层无执行体

- **挑战**：两重。①`lake exe cache get` 的历史行为面包含「无匹配缓存时打印提示但 rc=0」之可能（未实证排除）——此时 Prep 步绿、`lake build` 落入 mathlib 全量重编；410s/次先例（TB-04，GAPCLOSE §2.2-1）是**命中情形**先例，不约束 miss 情形。②草案全 workflow 无 `timeout-minutes`、步骤无 `timeout` 命令——GitHub 默认 job 超时 360 分钟；2 vCPU runner 上 mathlib 全量重编远超 3h，run 将在 12:08（wall 封钉）之后仍「在跑」，时刻表 09:10–09:40 绿灯窗空转、缓冲 55m 耗尽、11:30 硬收时 run 仍挂——**「wall ≤3h」目前只是日程表上的愿望，CI 层无强制体**。附带：超时杀后 `if: always()` 上传步骤会以 cache.log/build.log 存在而成功（`if-no-files-found: error` 只查全空），产出一个**无 verdict.txt** 的同名 artifact——分支丙（artifact 缺失）的检测口径「下载 404/名不符」不覆盖「包在而 verdict.txt 不在」形态。
- **依据钉**：W11 草案 §一 yaml（无 timeout-minutes，全文可 grep）；§一「TB-04 410s 先例」注（L36、L154）；W10″ 定稿 §二（09:10–09:40 绿灯窗、wall 硬封 ≤12:08 仅文字）、§三分支丙（缺失形态枚举）。
- **查验路径**：①合入前在 dry-run 中人为制造 cache miss（改 lean-toolchain 末位再复原）观察 rc；②grep workflow 确认无 timeout 钉（本席已做，确认）；③查 GitHub 文档/runner 既往 run 确认默认 360min 上限适用。
- **建议处置**：job 级 `timeout-minutes: 170`（≤3h 封钉留上传余量，数值为建议、由 orchestrator 定）；Prep 步加 cache 命中哨兵（解析 cache.log 计数行或构建时长上界断言，miss 即红转分支乙而非慢烧）；分支丙检测口径补「包内 verdict.txt 缺席即伪闭合」。

## §6 挑战：elan 用户态装脚本健壮性——无重试、无哈希钉、工具链下载混入 cache 步计时

- **挑战**：`curl -sSfL …/elan-init.sh | sh -s -- -y --default-toolchain none`：①公网单点无重试/退避，瞬时网络故障即红（属 fail-closed，可接受但挤占唯一一次重试预算）；②**安装脚本本体无 sha256 钉**——对照呈件 §二.1 对 elan tarball 钉 sha256（`37c2913c…`）的纪律，CI 侧装脚本反而裸 pipe 至 sh，供应链纪律前后不一；③`--default-toolchain none` 下 v4.35.0 工具链下载发生在 Prep 步首次 `lake` 调用时，与 cache get 同步同测——410s 先例不含工具链下载，首跑 Prep 段时长无先例支撑（与 §5 叠加放大 09:40 绿灯假设的未实证性）。
- **依据钉**：W11 草案 §一 yaml L65–68；呈件 §二.1（tarball sha256 钉先例）；GAPCLOSE §2.2-1（410s 先例语义范围）。
- **查验路径**：对照 m1-1-toolchain-spike.yml（先例载体，sha 67304cc46776）该段原文，确认先例亦无钉（若先例有钉而草案脱钉，则属移植失真，罪加一等）；elan-init.sh 是否提供固定版本 URL/校验值，查 elan 发布页。
- **建议处置**：装脚本落盘→sha256 对拍（钉值入 B-2 补钉件）→执行；curl 加 `--retry 3 --retry-delay 10`；Prep 步拆分为「工具链就位」与「cache get」两步分别计时留痕，为首跑时长建立真实先例。

## §7 挑战：artifact 名钉 × attempt=2 重跑 × org retention 上限——两处「钉而不死」

- **挑战**：①A4.1 设计 11-05 重跑记 `gha:<id>#2`——attempt=2 意味着**同一 run 的 re-run**；upload-artifact@v4 对「同 run 跨 attempt 同名 artifact」的行为（409 冲突／自动清理前 attempt 产物／须 `overwrite: true`）在案中**零实证**，且 v4 的行为史上变更过。若重跑时上传步骤 409 炸红，则 run 本体绿而 artifact 缺——恰落入 §5 所述「包在而件不全/无包」分支丙检测口径未全覆盖的形态。②retention-days: 90 是**请求值**；org/repo 级 artifact retention 策略若上限 <90 天将被静默钳制，「跨复审窗可援引」（GAPCLOSE §2.1）落空——无人实测 org 设置。
- **依据钉**：W11 草案 §一 yaml L134–146（名钉、retention 90）、§二 A4.1（attempt≥2 注记义务）、A1.3；GAPCLOSE §2.1 log_sha256 行（retention≥90 之目的钉）。
- **查验路径**：①11-03 预飞闸空转后**原地 re-run 一次**（attempt=2），实证上传步骤行为——此动作零成本且本就在空转窗内；②API `GET /repos/{owner}/{repo}` 之外查 org actions 权限/retention 设置（须 orchestrator 权限，列入其合入前检查单）。
- **建议处置**：①实证前 A4.1 注记条款旁加「attempt=2 上传行为未实证」警示；若 409 实证，artifact 名改带 attempt（`m1-b1-comparator-run-a<attempt>`）并对拍 A1.3 下载键同步修订；②retention 实测值入回填登记（名值分离：策略值与请求值分列）。

## §8 挑战：`lake comparator` CLI 未实证——草案「仅改命令行，规程不动」的缓解断言过强（重点攻击）

- **挑战**：W11 草案 §一末如实登记调用面未实证，并称「若实调形态不同，仅改 `Comparator run` 步骤命令行，tee/sha256/verdict 规程不动」。红队判此缓解**不成立的一半**：若实调形态的**出口码语义**不同（如 comparator 以非零码表达 rejected、或以零码＋stdout 文本表达、或 verdict 行拼写非 `verdict: accepted` 小写形态），则失效的不是一行命令而是——①verdict grep 正则（§2 之取值根）、②GAPCLOSE §2.1 `verdict` 字段「出口态 accepted/rejected」定义、③验证规程 4 的对拍基准、④spike B §5.1 在案拼写钉本身。即：**调用面不确定性沿 verdict 链路上传至字段 schema 层**，「规程不动」只在「仅参数不同、出口语义相同」的窄情形下成立。更甚者：若 comparator 根本不在 `library/ns` 拷贝项目内可解析（它若属 nanoda_lib 或其它包），草案在 /tmp/m1-b1 内调用即 127——§1 之闸缺位下该失败以「VERDICT PARSE FAILED」红在 Verdict 步，失败归因被误导至解析层而非调用面层。
- **依据钉**：W11 草案 §一末「如实登记」段；GAPCLOSE §2.1 verdict 行（固定值 `lake comparator`、出口态拼写钉）；GAPCLOSE §4.3-3（nanoda 复核器跑批——提示 comparator 与 nanoda 族的可能关系，草案未交代）。
- **查验路径**：仓内 `grep -rn "comparator" lakefile* library/ scripts/ .github/`，定位 comparator 子命令/目标的定义件与出口码语义；对照 spike B §5.1 原始实录确认 `accepted/rejected` 拼写的实证出处是 stdout 行还是出口码。
- **建议处置**：11-03 预飞闸前将「comparator 调用面核一遍」从建议升格为 B-1 闭合**前置要件**（或排进 dry-run 的检查单首项）；调用面实证结果（命令行、出口码表、verdict 行拼写）落 B-2 补钉件新增第十一钉；dry-run 即按实证形态跑，禁以未实证形态空转充四要件实证。
