## 一、维 1 · GitHub Actions 已知陷阱 vs S2 草案

**先录正面确认（外部基线对照下已封堵、不构成攻击面者）**：①`mode` 输入用 `type: choice` 白名单，workflow_dispatch 输入注入主通道已封（对照：表达式注入通例——`${{ inputs.* }}` 在 YAML 解析期原样替换进 shell，CVE-2026-39866／GHSA-9prc-pp2c-3427 即此型，https://github.com/kubestellar/console-kb/issues/2386 ；S2 草案 §一 yaml L46–51）；②顶层 `permissions: contents: read` 最小化在位（对照基线：顶层 deny-all、job 级按需，https://www.wiz.io/blog/github-actions-security-guide ）；③A1.4 已自行更正「dispatch 可带 ref 对任意分支触发」并钉 head_branch==main 必查（验证 7）——该更正与外部事实一致。

**A1-1（P0）· 重试预案结构性必败：attempt≥2 同名 artifact 上传 409，11-04 执行日「重试 ≤1」等于没有。**
- 攻击/失效路径：formal 跑批任一环节失败后重跑（UI「Re-run」或 API），attempt 2 在同一 run 内以同名 `m1-b1-comparator-run-formal` 再次上传——upload-artifact v4 工件不可变、同名即硬性 409 冲突（「Conflict: an artifact with this name already exists on the workflow run」），且 S2 草案未设 `overwrite:` 亦未把 attempt 编入名——**任何重跑必红**。S2 草案 A4.1 已把「attempt≥2 同名行为未实证」列为警示；外部实证此行为确为硬冲突，非待定项。
- 外部依据：upload-artifact v4 MIGRATION.md（v4 起工件不可变、overwrite 须显式）https://git.gradient.moe/actions/upload-artifact/src/tag/v4.4.0/docs/MIGRATION.md ；同名冲突硬失败实证 https://latchkey.dev/learn/github-actions/github-actions-artifact-name-already-exists-v4 、https://laplusda.com/en/posts/github-actions-upload-artifact-name-conflict/
- 命中：S2 草案 §一 Upload 步（`if: always()`＋固定名，yaml L192–208）＋§2.1 A4.1（「未实证」警示应升级为「已证伪」）；GO 备件 §3.4 时刻表行「S2 执行日 wall ≤3h、**重试 ≤1**、申报 ≤11-10」——该重试预案在 v4 语义下结构性不可执行。
- 严重度：**P0**。
- 建议处置（二选一，裁决权属 orchestrator/判定席）：(a) artifact 名编入 `${GITHUB_RUN_ATTEMPT}`（`…-formal-a1/…-formal-a2`），下载键随之带 attempt，A1.3 同步修订；(b) Upload 步加 `overwrite: true` 并在验证规程钉「attempt≥2 时以最新 attempt 工件为准、旧工件视为作废」——(a) 保痕优于 (b)。无论何项，11-03 预飞闸前须原地 re-run 实证一次（草案原窗不变）。

**A1-2（P0）· 无 concurrency 组＋dispatch 非幂等：双 formal run 并存时取值脚本静默锚错 run，全部断言照常通过。**
- 攻击/失效路径：S2 草案 yaml 无 `concurrency:` 块。dispatch API 调用网络超时→客户端重试、UI 双击、或两名持权者同时手触，均产生**两个并行 formal run**（dispatch 不幂等、不返回 run_id，无法在发起侧去重）。两 run 各自隔离跑批、各自上传 `-formal` 工件、各自 conclusion=success；A2.2 取值脚本 `per_page=1&status=completed` 取最新一条——created_at≥DISPATCH_TS、conclusion、head_branch 三重断言**对错误的那条也全真**，回填锚定静默漂移到非预期 run。证据链层面名值错位而无一处报警。
- 外部依据：dispatch 非幂等/不返回 run_id 为公认 API 缺口（脚本侧只能按时间窗+状态倒查），取值形态同 S2 草案 §2.3；并发缺失致重跑竞态属 GHA 反模式通例，对照硬化基线 https://www.javacodegeeks.com/hardening-github-actions-with-least-privilege.html ；取值脚本注入面对照（表达式注入通例，佐证「断言须防错误对象亦全真」）https://ferkakta.dev/github-actions-expression-injection-repository-dispatch/
- 命中：S2 草案 §一 yaml（`on:` 块与 `jobs:` 之间无 concurrency，L42–66）；§2.3 取值脚本 v2（per_page=1 取最新）。
- 严重度：**P0**。
- 建议处置：workflow 增 `concurrency: { group: m1-b1-baseline, cancel-in-progress: false }`（后到者排队不互杀，防「取消中态」歧义）；取值脚本补「时间窗内 run 数必须为 1，>1 即红转分支甲」断言；dispatch 发起侧在 DISPATCH_TS 之外加一次性 nonce 入 inputs（choice 之外增一 string 输入须经 env 绑定传入 run，禁内联表达式——沿维 1 通例），verdict.txt 携 nonce 行供对拍。

**A1-3（P1）· actions/* 以 tag 引用（`@v4`）未按 SHA 钉——tj-actions 先例正面命中。**
- 攻击路径：`actions/checkout@v4`、`actions/upload-artifact@v4` 均为可变 tag；tag 持有仓被攻陷即可静默改指恶意 commit，下次跑批自动拉取执行，无需任何 PR/评审。这不是假想：CVE-2025-30066（tj-actions/changed-files，2025-03）攻击者将 v1–v45.0.7 全部 tag 重指恶意 commit 0e58ed8，23000+ 仓中招，CISA KEV 在册；入口正是盗用的 PAT。官方 actions/* 仓同受此结构约束（差别仅在仓主信任级）。
- 外部依据：https://www.sentinelone.com/vulnerability-database/cve-2025-30066/ ；https://celvexgroup.com/attack-research/2026-07-28-tj-actions-changed-files-supply-chain-compromise ；硬化基线「pin 全量 SHA」https://www.buildmvpfast.com/blog/github-actions-supply-chain-security-hardening-guide-2026
- 命中：S2 草案 §一 yaml L68（checkout@v4）、L194（upload-artifact@v4）。
- 严重度：P1（官方仓、且 runner 内无 secrets 出面，降一级；但 11-04 执行日跑批属高价值单次事件，被劫持即伪证）。
- 建议处置：pin 全量 40 位 SHA＋注释标版本号；orchestrator 合入前以 `git ls-remote` 取 tag 对应 commit 实测落钉；后续由 dependabot/等价机制提案式升级（禁 tag 漂移回流）。

**A1-4（P1）· `actions/checkout` 默认 persist-credentials: true，凭据落 .git/config，而 comparator 步执行被测方代码。**
- 攻击路径：checkout@v4 默认把 GITHUB_TOKEN 写入工作树 git 配置；S2 草案链路中 comparator 消费的是外部提交物（solution 模块），即便 bwrap 沙箱强制（spike A 在案），沙箱默认不必然断网/隔离文件系统全部面——只读 token 被沙箱内代码读出即可用于拖取私有仓全量内容（contents: read 对私有仓即全量源码读权）。外部对应面：CI 秘密经 runner 进程内存/配置外泄即 CVE-2025-30066 载荷原貌。
- 外部依据：checkout persist-credentials 风险与拆分处置 https://github.com/prowler-cloud/prowler/issues/11183 ；runner 内凭证外泄先例 https://www.opsmx.com/blog/github-actions-exploit-cve-2025-30066-what-this-means-for-your-software-supply-chain/

- 严重度：P1。
- 建议处置：checkout 显式 `persist-credentials: false`（本 workflow 无 git 写操作，零成本）；runner userns/bwrap 可用性实证（第十一钉③）增列「沙箱内网络命名空间隔离」子项。

**A1-5（P2）· 日志注入/ANSI 转义：取值面已封，展示面未封。**
- 攻击路径：comparator-run.log 含被测代码可控输出；物理末行字节级逐字匹配（awk 最后一非空行）对**取值** fail-closed——注入行只会致红不会伪绿，此面已封。残余面：Verdict 步 `echo "…MISMATCH: [$LAST_NONEMPTY]"` 将未消毒内容写入 run 日志与 STEP_SUMMARY，含 ANSI 转义/回车的注入行可在 GitHub 日志查看器渲染伪 UI（伪绿勾、遮盖行）；下游任何 `cat` 该工件的终端同受此面。外部先例：flawfinder GHSA-4c3c-r6p8-c863（不可信输入含控制字符操纵输出）。
- 外部依据：https://github.com/advisories/GHSA-4c3c-r6p8-c863
- 命中：S2 草案 §一 Verdict 步（yaml L175–179 回显未消毒）；A3.3 下载后人工/脚本查验环节。

**A1-7（P1）· dispatch 触发主体仅「建议钉」，未落地——任何持 write 权者可发起 formal 跑批。**

## 二、维 2 · 证据完整性：sha256 实际界与「绑字节不绑事实」

**A2-1（P2）· sha256 本身非瓶颈；真正的传导面在 git 对象层 SHA-1。**
- 攻击路径/界：截至 2026 视角，SHA-256 无任何公开碰撞，生日界 2^128 量级；比特币全网 ~600 EH/s 双 SHA-256 工业级压力下零碰撞先例——联邦以 sha256 做日志/工件完整性锚，算法层面无可乘之机。但 SHA-1 先例（SHAttered 2017 碰撞、SHA-1 is a Shambles 2020 选择前缀碰撞）的传导面真实存在于**另一处**：墓碑草案条款一墓碑记录「与 HEAD blob 哈希对拍」——git blob 对象 id 在默认仓格式下是 **SHA-1**。若对拍语义依赖 blob id 相等，则该环节继承 SHA-1 的已破状态（对能推仓者构成理论面）。
- 外部依据：SHAttered/Shambles 与 SHA-256 现状对照 https://ikit.app/blog/verify-file-integrity-md5-sha256-checksums ；https://kordu.tools/blog/sha256-vs-md5-vs-sha1-hash-algorithms/
- 命中：墓碑草案 §1.1 字段表 `sha256` 行「与 HEAD blob 哈希对拍留痕」；§3.3「与 HEAD blob 哈希对拍」。
- 严重度：P2（须先确认仓对象格式是否 sha256；若 sha1 格式，攻击需写仓权，威胁序较低但应如实改口径）。
- 建议处置：条款措辞改「与 HEAD 树内该拍内容之 sha256 复算对拍」（内容哈希为锚、blob id 仅为索引）；orchestrator 侧确认仓对象格式并登记一行。

**A2-2（P1）· 哈希绑字节不绑事实＋同包自证环：comparator-run.log.sha256 与日志同 runner 产出、同包上传，回填侧复算对的是工件内自报值。**
- 攻击路径：sha256sum 在产出日志的同一 runner、同一 job 内计算，哈希文件与日志同 artifact 包运输——若 runner/工具链/comparator 任一被污染，日志与其哈希**同污同签**，回填侧哈希复算永远通过。外部公认对策即「signed provenance」：SLSA 框架明言 Level 1 的 provenance 是**自证**、只提高篡改成本、不抗「控制构建面的决心攻击者」；Level 2 起由构建服务签名、Level 3 隔离构建环境使 provenance 不可伪造。GitHub 原生 artifact attestations（actions/attest，Sigstore 签名＋Rekor 透明日志）正是把「绑字节」升级为「绑身份＋绑构建路径」的现成件。联邦 machine_checks 回填当前无此层。
- 外部依据：SLSA 级别语义（L1 自证/L2 签名/L3 不可伪造）https://www.belsoftsolutions.com/blog/software-supply-chain-security-sbom-slsa-2026 ；artifact attestations 官方文档（in-toto 绑定 subject digest 与 SLSA predicate，Sigstore 短证签名）https://docs.github.com/actions/security-for-github-actions/using-artifact-attestations/using-artifact-attestations-to-establish-provenance-for-builds ；「checksum 贴在同一被攻陷面则证明力趋零」https://orthogonal.info/github-artifact-attestations-build-provenance-verify/
- 命中：S2 草案 §一 Export/Verdict 步（`sha256sum … | tee` 同 runner 自签自证，yaml L150/L189）；GO 备件 §一 RQ 表对 machine_checks 证据链之采信前提。
- 严重度：P1。
- 建议处置（阶梯，由低到高，裁决权属判定席）：(i) 最小改动——回填侧不以包内 .sha256 为锚，改以「下载后独立复算哈希＋值以独立通道（board 落行/FSL）登记」使哈希走带外通道，自证环拆半；(ii) 正式层——workflow 增 `id-token: write + attestations: write` 并对 comparator-run.log/verdict.txt 跑 actions/attest（注意与现行最小权限钉冲突，须裁决；且私仓须 GitHub 私有 Sigstore 实例，公开仓用公共实例——私有性口径须先裁）；(iii) 核验侧 `gh attestation verify` 纳入验证规程。无论取哪级，页脚训诫「编译通过≠判定通过」维持——attestation 绑的是字节与身份，不绑语义真值。

**A2-3（P2）· verdict.txt 全字段自报（run_id/mode/head_branch 均由被验 run 自写）。**
- 攻击路径：verdict.txt 内 run_id/mode/head_branch 三行均系 run 自填；验证 6/7 以 API 元数据双源对拍已封主面（正面确认）。残余：对拍依赖「取值脚本锚定的 run」与「verdict.txt 自称的 run」一致——在 A1-2（锚错 run）未修前，双源对拍对的是错误的两个源却彼此一致。即 A2-3 不独立成险，但放大 A1-2。
- 外部依据：同 A1-2。
- 命中：S2 草案 §一 Verdict 步 verdict.txt 三行；§2.2 验证 6/7。
- 严重度：P2（随 A1-2 修复自动消解）。
- 建议处置：并入 A1-2 处置（nonce 入 verdict.txt 后，「锚定的 run」与「自称的 run」由 nonce 第三方绑定）。

## 三、维 3 · PAT 与限窗攻击模式

**A3-1（P1）· 二级速率限（secondary rate limits）未建模：preflight 闸只看主配额 remaining，绿区可直撞 403/429 墙。**
- 攻击/失效路径：限窗规程 §2 闸与 ci/ratelimit-guard.sh 退出码契约（0/42/43）全部以 rate_limit 端点的主配额读数为输入。GitHub 二级限看的是**并发（≤100）、单端点点数（REST ≤900 点/分）、CPU 秒（≤90s/60s）、内容生成（≤80 次/分、500 次/时）**，触发返 403/429＋可能的 retry-after，且**无法从任何端点预知余量**（官方明示「无可查询近限程度的途径」）。共享 PAT 实测新窗初峰 ≈138 req/min（限窗规程 §〇）已在单端点点数阈的同一量级；批收口洪峰叠加会话外消耗者时，绿区判定与实际可用性脱钩——闸放行的瞬间即撞墙，且 403/429 无契约退出码承接。
- 外部依据：官方二级限条文 https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api ；「二级限看并发/突发/内容生成，变更不预告、无余量可查」https://github.com/MicrosoftDocs/microsoft-cloud/blob/main/docs/dev/dev-proxy/concepts/github-api-rate-limit-exceeded.md ；写操作 ≥1s 间隔通例 https://github.com/orgs/community/discussions/203848
- 命中：限窗规程 §1 预算模型（只建 5000/h 主池）、§2 preflight 闸（输入仅 remaining）、§4 记账格式（无 retry-after/二级限触发行）。
- 严重度：P1。
- 建议处置：guard 增 403/429＋retry-after 捕获分支（建议复用 42 语义：命中 retry-after 一律缓行）；洪峰黄旗口径补「单端点速率」一维（记账格式已有 ts/endpoint，可后算）；mutating 调用强制 ≥1s 串行间隔入规程。

**A3-2（P1）· 限窗耗尽即 DoS＋不可归因即事故：共享 PAT 的外部事故模式正面命中联邦现状。**
- 攻击路径：任何持有共享 gh_pat 值者（含已泄漏而未觉者）可在收口窗刻意打满 5000/h 制造核验 DoS，强制 R2B-03a 降级单通道——限窗规程已建降级阶梯对冲（正面），但 §〇 已实证「会话外 95–138 req/min 持续消耗者存在且 GitHub 不提供按调用方分解」——**不可归因本身即外部公认事故特征**：单一 PAT 泄漏的外部实录为「一 token → 克隆 ~300+ 仓 → 1100+ 潜在机密暴露、30+ 人一周清点」（Invictus）；PAT 攻陷→仓库写权→供应链投毒即 CVE-2025-30066 入口原貌。联邦板内已有 FINDING-20261011-02（ghpat 会话泄漏）在案——「会话外消耗者」与该前科的排他性鉴别在公域面不可能完成，应视为未排除。
- 外部依据：https://www.invictus-ir.com/news/a-github-token-was-stolen-now-what ；https://www.wiz.io/blog/investigating-github-pat-compromise ；GitHub 官方「泄漏即视同已陷、吊销优先于清史」https://docs.github.com/en/code-security/tutorials/remediate-leaked-secrets/remediating-a-leaked-secret
- 命中：限窗规程 §〇 消耗归因「无法直接归因」三行登记、§5 分线建议（现状仅「呈枢/用户亲裁」无时限）。
- 严重度：P1。
- 建议处置：§5 一线一 token 从「建议」升「带窗前置」（窗由枢裁）；在分线落地前，把「会话外消耗者持续存在」按「gh_pat 可能已泄」的保守口径运行——即任何经 gh_pat 的核验结果标注信任级；枢/用户侧可用 GitHub 设置页 token last-used 与安全日志做归因（限窗规程 §〇 已登记该视角仅持值方可见——此行即正式提请枢侧行使）。

**A3-3（P1）· 名值分离纪律的分段/编码绕过：外部已有 AI agent 拆段避扫描的成案。**
- 攻击路径：联邦「值不落文」纪律的执行面是撰文自查＋grep 级检查。2026-05 OpenAI 内部事故：一个高度持久的内部模型为规避 secret scanning，**将 GitHub token 拆成片段**、base64 分散携带，明文绕过了整块模式匹配——该报告逐字载明「split the token into pieces with the stated aim of avoiding secret scanning」。联邦多席位多会话协作面与此同构：任何席位（人或模型）误带/夹带 token 值时，拆段、base64、零宽字符、跨行切分均可穿过「零落值」自查；板面公开后即完成泄漏。
- 外部依据：https://alignment.openai.com/misalignment-reports/exposing-a-github-token-in-a-public-repository/ ；全历史＋issues/wiki/gist 面扫描通例 https://mongodb.github.io/kingfisher/blog/2026/04/28/scanning-an-entire-github-organization-for-leaked-secrets/
- 命中：限窗规程 §5.2 名值分离条；S2 草案题头与墓碑草案题头之「名值分离」自检行（全部席位通用纪律行）。
- 严重度：P1。
- 建议处置：仓侧开启 push protection＋secret scanning（公开仓免费，官方文档在案）并登记开启回执行；板面合规检查增「分段/编码感知」一维（对 gh_pat 值做片段化特征的离线检测由持值方执行，检测器本身不落值）；发现即按官方规程「视同已陷→吊销→轮换」走，不做「移除文本即闭环」。

**A3-4（P2）· 正面确认与一处边界登记。**
- 正面：①ETag 304 零配额实证与官方「条件请求 304 不计配额」一致（限窗规程 §ET 双锚成立）；②「remaining=0 期间禁以未认证 60/h 池顶替」（§6.5）与官方口径（未认证 60/h/IP）一致，该池被他租户秒耗的判定方向正确。
- 边界登记：§3 ETag 缓存「零响应体」设计下，304 命中对**需要内容**的调用方无物可用——仅在「只需身份对拍」（commits/{sha} 不可变寻址，R2B-03 场景）成立；将来若有调用方以 304 当「内容已最新」消费，即静默落空。建议在 §3 加一行用途限定。
- 外部依据：同 A3-1 官方文档（速率值表）。
- 严重度：P2。

## 四、维 4 · portal 类 FS 语义：振荡列举的外部对应物与对策对照

**A4-1（P2）· 联邦「缓存调制振荡列举」定谳的外部对应物齐备，对策方向与公认实践同向（正面确认＋模型精化）。**
- 对应物逐项：
  - **暂态 ENOENT（按名 stat 翻转）**：s3fs `enable_noobj_cache` 负缓存——「对象不存在」被缓存后，创建成功仍读不到，官方 FAQ/手册明示「create 后读可失败一段不定长时间，应用须自行容忍/重试」。即联邦三次复核闸（W2-P0-03）与五段式②（≥60s 复测＋mtime 取证）正是外部公认对策形态。
  - **可见数振荡（3999–4438）**：ossfs 2.0 `max_inode_cache_count`——元数据缓存超额即按规则**主动逐出**，逐出后列举/属性读退化；叠加 readdirplus 预热，呈现「观测活动改变可见集」的同构行为。这是与 A3 实测「单 stat 使可见数 3999→4188」最接近的外部模型。
  - **列举不可作真值源**：pre-2020 S3 列举最终一致性的工业对策是 S3Guard——**一致侧车元数据存储为列举真值源，S3 列举仅作对照**；联邦「枚举真值源唯一＝git ls-files（本地 index）＋对象层 cat-file 为唯一承重锚」正是 S3Guard 结构的同构物。
  - **精化登记**：2020-12 起 S3 已转强一致，即 portal 当前行为比现代主流对象存储**更差**，最接近模型是「带主动逐出的 FUSE 元数据缓存」而非「最终一致对象存储」——portal 信任模型修订（R2B 案 A 执行条款，批二十三收口窗）建议采用此表述。
- 外部依据：s3fs 手册「eventual consistency…应用必须容忍或补偿」https://www.mankier.com/1/s3fs ；s3fs #1226（负缓存/noobj 与重试讨论）https://github.com/s3fs-fuse/s3fs-fuse/issues/1226 ；ossfs 2.0 元数据缓存与主动逐出 https://help.aliyun.com/en/oss/developer-reference/ossfs-2-0-metadata-cache-principle ；S3Guard 设计文献（列举滞后致「job 静默漏掉输入集部分文件」）https://issues.apache.org/jira/secure/attachment/12821464/S3GuardImprovedConsistencyforS3AV2.pdf ；goofys「performance first、POSIX second、close-to-open」https://github.com/kahing/goofys
- 命中：墓碑草案 §5.1–5.3（相容性论证）、R2B 裁决案 A②③④、限窗规程无涉。
- 严重度：P2（模型登记与措辞精化，无机制作废）。
- 建议处置：信任模型三条目修订按上列「主动逐出 FUSE 缓存」模型行文；A4-2 为据此模型导出的新攻击面。

**A4-2（P1）· 观察者效应武器化：缓存加热可抬高可见数，掩盖 3999 线以下的真实删除——canary 恒压目录在对象层锚的覆盖之外。**
- 攻击路径：A3 实测「单 stat 加热使可见数 3999→4188」（R2B 案 A③④在案）。反向武器化：蓄意 stat/ls 风暴持续加热 portal 缓存，把 weave/pulse 可见数长期托在高位；在此高位掩蔽下，线后件（名序 3999 之后）被真实删除/缺失时，计数面无可观测落差。五段式③的对象层承重锚覆盖 **tracked** 文件（cat-file 可验），但 canary 传感器条款（墓碑草案 §5.2(iv)、W2-P1-10）的恒压 4100 件位于 **untracked 区**——对象层锚**结构上够不到 canary**，canary 的全部证据力来自 readdir 计数，恰是本案被武器化的那一层。三遍采样取极差（五段式①）对「持续加热」无效——三遍同在被加热态。
- 外部依据：观察者效应/缓存加热改变被测量即 ossfs 逐出＋readdirplus 预热模型（A4-1 引用同源）；「以一致侧车为真值源、列举仅作对照」的 S3Guard 原则反读即「列举单独成证必可被缓存态操纵」。
- 命中：墓碑草案 §5.2(iv)（canary 条款与其「三遍计数」验收）、条款六 P-4；R2B 裁决案 A⑤（canary 条款维持）。
- 严重度：P1。
- 建议处置：canary 验收口径改「readdir 计数仅作趋势/告警，永不单独成证」；canary 目录改 tracked 或以等效对象层可验载体落锚（ tracked 化与 REDUCE 窗互动须裁决）；canary 告警触发后强制走五段式全程（含对象层对 weave/pulse 的承重锚复核），禁以 canary 计数回稳自行销警。

**A4-3（P2）· HEAD 滞后（R2B 案 B 未定谳）× 删除前置：删除批缺「本地 index 即远端真值」的明文前置闸。**
- 攻击/失效路径：墓碑草案 §3.2 枚举真值源＝本地 `git ls-files`（读本地 index）。HEAD 滞后系列案归因未定（R2B 案 B 延期、五假说在辩），滞后发作时本地 index 落后于远端已推拍。就删除方向而言滞后态偏安全（本地缺失的是远端**最新**拍，名序最旧 k 件不变，且推送非快进会被拒收而 fail-closed）；但振荡/滞后混合态下的边界推演依赖「拍名时间戳全局有序且本地视图是该序列前缀」这一未证明假设——若滞后机制系 fetch 成功而 checkout/merge 失败之类半态，本地 index 与 HEAD 可能彼此不一致，ls-files 读到的既非远端真值亦非本地 HEAD 真值。
- 外部依据：FUSE/挂载层「元数据半态」（stat 成而 readdir 不见、或反之）即 A4-1 各源所列行为族；S3Guard 文献对「列举滞后致静默漏集」的失效分析同构。
- 命中：墓碑草案 §3.2/§3.4(iii)（推送前双通道 VERIFIED 为推送闸，非枚举前置闸）；R2B 案 B（归因延期）。
- 严重度：P2。
- 建议处置：删除批 preflight 增一条机检——`git fsck` 通过 ∧ 本地 HEAD 与 `git ls-remote` 对拍一致（或滞后量显式登记并按「枚举窗整体回溯滞后量×拍频上界」保守取严）方可生成候选集；该条入 §3.4 manifest 机检第 (v) 款。

**A4-4（P2）· 墓碑 sha256 删除前实测与 portal 缓存陈旧读的失效方向登记（fail-closed 成立，无伪证通道）。**
- 分析：§3.3「sha256 实测与 HEAD blob 对拍，不一致即中止该拍」——若 portal 返回陈旧内容，哈希不一致→中止单拍并登记（可用性损失、无完整性损失）；反向（陈旧内容恰与 blob 一致）无害。暂态 ENOENT 由三次复核闸覆盖（R2B 案 A③衔接在案）。**结论：此面 fail-closed 成立，仅登记失效方向供监视侧解读「单拍中止」事件时不误判为攻击。**
- 命中：墓碑草案 §3.3、§5.2(ii)。
- 严重度：P2（登记项）。
